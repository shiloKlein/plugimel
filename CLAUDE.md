# Platoon helper

Hebrew RTL helper for a platoon/company: who is in/out, auto guard roster (שמירות), requests, equipment (ציוד, sergeant). Plain ES modules, no bundler, no framework, no tests. The app is the static site in `app/www/` (an installable PWA: `manifest.webmanifest`, `sw.js`, `icons/`), published to GitHub Pages by `.github/workflows/pages.yml`. The site holds no data. An Android build via Capacitor (`app/`, same setup as `../tshuva-helper/app`) is optional and no longer the main route. All relative URLs, so it works under a `/repo-name/` path. Everything works offline; data is one JSON object in `localStorage` (`lib/store.js`).

- `app/www/lib/scheduler.js` is the roster algorithm. It has no DOM code, so it can be tried in node. Shift points = hours × weight (night/evening/day). The lowest points inside the rolling window (`settings.windowHours`) gets the seat. Hard filters: absent, overlapping shift, missing qualification. Soft penalties added to the score: short rest, night after night, "not together" pairs. Soldiers new or back from absence start at the window average. `assess()` re-checks existing shifts live, so the roster shows yellow/red chips when something changes.
- Posts have a `kind`: `guard` (recurring, auto-filled), `patrol` (סיור) or `mission` (יזומה). Patrols/missions are never auto-generated; staff add them by hand ("הוסף" in the roster) and may define `roles: [{label, qual, n}]` (qual may list alternatives with commas, e.g. `סמל,מ"מ`). A shift keeps `roles: {soldierId: roleIndex}` and an optional `note`. Placing someone by hand uses `candidates()` in scheduler.js: every active soldier is listed (free first, lowest points first) with points, previous/next shift, same-day shifts, and conflict/soft warnings; conflicts need a confirm but are never blocked.
- Presence planning by date (from today on): `lib/presence.js` (`setPresence` cuts/splits overlapping absences; type `present` cancels), UI `views/presenceplan.js` (pick soldiers or a whole מסגרת, status, first/last day). Opened from the calendar button and a soldier's sheet. The day sheet lists everyone split into in/out of base, each with a ⋯ menu (this day in/out, or a range: calendar picker for first/last day, then a confirm sheet with the status; `rangeFlow` in presenceplan.js). Equipment type icons: `lib/gearicons.js` (`gearIcon(type)`, name-matched line drawings, generic box as fallback); a soldier's equipment sheet has "הוסף ציוד" opening an icon grid, tapping one opens the add form with that soldier as holder. Equipment screens: search by name or serial, grouped by מסגרת, item status filter, sign/return from a soldier's sheet.
- Sync compares the Drive file content checksum (`md5Checksum`), not `version` (Drive bumps version by itself, which looked like a conflict). `rev` counter keeps edits made during an upload marked unsaved.
- `lib/store.js` holds the permission table (`PERMS`). Roles: admin, officer, sergeant. Soldiers don't log in and only view. The login (`lib/auth.js`) only changes what the UI shows. The real access control is meant to be Drive folder sharing (Viewer for soldiers, Editor for staff).
- Views are in `www/views/*.js` and export `render(el, ctx)`. Each assigns `el.onclick`, not addEventListener, because `render` is called again on every data change.
- Soldier = first/last name + `place` (מסגרת: מ"מ/סמל/כיתה א..) + `job` (תפקיד: מ"כ/נגב/קלע..) + `service` (מלא/חלקי/סטודנט). A job also works as a qualification for posts. Places and jobs are editable lists in settings. `state.round` = the service round (start/end); `newRound()` in store.js resets a round and keeps soldiers. Names are imported by pasting (`parseNames` in views/soldiers.js).
- `views/calendar.js` + `lib/hebdate.js` (copied from tshuva-helper) give the Hebrew calendar with holidays, expected presence per day and job coverage.
- Drive sync: `lib/sync.js` (no DOM/Google, tested with a fake Drive: conflict = Drive file version moved while we have unsaved changes), `lib/drive.js` (Google Identity Services token flow + Drive REST + Picker, scope `drive.file` only), `lib/syncui.js` (the sheet), `lib/config.js` (client ID / API key / project number, public by design). The whole state is one JSON file `plugimel-data.json` in a Drive folder `plugimel`; the first phone creates it, others pick it with the Google Picker. Google Cloud project `plugimel` (number 438526458930), consent screen still in Testing: only listed test users can sign in and sign-in lasts 7 days; publish it to remove that.
- Equipment: two kinds. Numbered items (`settings.equipTypes`, one record per item with `serial`) and counted personal gear (`settings.gearTypes`, one record per type+holder with `qty`; the חתימות grid edits these). Both catalogs come from the user's Excel and are editable in settings. Soldier paste import columns: first | last | job | place | email (also a .txt/.csv file picker; Excel CSVs are decoded as UTF-8 or windows-1255). `soldier.email` is how a Google login will be matched to a soldier; it lives in the staff file only. When the soldier view file exists, publish a hash of the email, never the email itself.
- Permissions (`PERMS` in lib/store.js): admin = owner of the app (users, backup/restore, wipe); officer and sergeant can do everything with the data. Soldiers (not logged in) see only the roster, calendar (holidays, round, guard list), soldiers (no presence) and equipment. Presence (who is in/away and why), requests and checks are staff-only. This is UI-level until the soldier view file exists; the staff file itself holds everything.
- Daily equipment checks: `lib/checks.js` (pure, tested), `views/checks.js` (sergeant ticks per soldier/item: found / with the soldier outside the base + note / missing), history strip, green/red per day in the calendar. Checks are configurable in settings (default: רימונים, and צל"מ = all numbered types). `settings.checksFrom` switches them on. WhatsApp reminders are `wa.me` links (one tap per soldier, or a group message to copy): the app cannot send WhatsApp by itself without a paid server API.
- Transfers (`views/transfers.js`, `state.transfers`): a request that only moves the item when the sergeant approves. Staff create them now; soldiers will create them from their own phones in the soldier-side stage.
- `views/daysheet.js`: the day sheet (presence with reasons, pending requests with approve/deny, guard list, checks), opened from the calendar and from requests.
- Demo data is `lib/demo.js` (`state.demo` is set). It can be deleted from Settings.

- UI: mobile first. Bottom tab bar on phones (with an "עוד" menu for requests/settings/login), sidebar from 900px. Design tokens and dark mode are at the top of `styles/app.css`. Icons are inline SVG from `lib/icons.js`; `avatar()` in `lib/ui.js` gives the colored initials circle.
